# llm-ime: pitfalls

- Training formats where the model decides as it reads (interleave): give the inputs it reads a loss too (`train.py --key-weight`), or the score never pays for a wrong segmentation or for keys that do not fit (r4b: dao read as 大哦).
- The base model must score whole sentences with its own tokenization; fed one character per token it underrates characters it normally writes inside a longer token (还 of 还有).
- Reading the keys other than as typed (a swap, later typos): the fine-tuned model sees the typed keys in its prompt and scores against them, so a corrected reading needs a search with the corrected keys in the prompt (`swap_margin` in `ime/llm.py`); scoring it under the typed prompt, or by the base model alone, loses. An extra reading (嗯 as en, `ngram.EXTRA_READINGS`): standard keys in the prompt, but the search still walks the typed keys and keeps only results that use the extra reading; else the beam fills with what the standard keys read (n: 你 / 那). Typo readings (5B.8: a key too many, missing, or next to the right one) only for keys that cannot be read as typed, in rows of their own beside the beam (`typo_rows`), and not where a swap reads a syllable: else they push out abbreviations (zl yi read as li) and swaps (zheyagn as yag 样 + n 呢).
- A common word the fine-tuned model puts far behind (jigexian 及格线: 几个 first, 20-30 nats) cannot be lifted by a bonus, a floor on the first token, or a temperature on its logits: the plain set drops 6-28 points, or the word stays out of the beam. The whole-word candidate (`word_top`, `_whole_words`) goes in after the search, at place 5 (6B.7); the cause is in the model (7B.1), `scripts/token_scores.py` shows it token by token.
- Retraining against that sureness (7B.1): label smoothing does not move it (0.1 over the vocab floors tokens at −14, below 及's −11.7), and a token-level teacher from the base model (`train.py --key-teacher`: the base over the tokens the keys can still read) is capped by the base's own first step, which cannot see the keys ahead (及 −7.4, rank 129 after 「只是到了」), and costs the plain set 2-3 points.
- `valid` is only comparable between runs with the same loss: it includes the KL term with `--teacher`, and the boundary cost of the letters with `--key-weight`.
- Before a full run of a new format: a few hundred steps, then `run_eval.py --limit 20` against the same 20 items of a known model.
- Remote `pgrep -f` / `pkill -f`: the pattern must not appear in your own ssh command line, or it matches itself (a wait loop never ends, pkill kills your ssh).
- dgx is unified memory: `--mem-frac 0.4` and `scripts/memguard.sh 12` beside training. Look at `nvidia-smi` on lab4090 / lab4090b first: other projects' training fills them.
- home4070 (the user's own 4070, 6A.1): the card is at ~7.45 of 12.3 GB before we start (voice-tts and Windows, which WSL's `nvidia-smi` does not list). LoRA only: `--lora 16 --ckpt --tokens 4096 --ce-chunk 256 --mem-frac 0.30` (2.2 GB); voice-tts gets slower while it trains, so train at night and not while the user games.
- The weekly retrain (6A.2, `scripts/retrain.py` on M4 every hour, installed by `scripts/install_retrain.sh` from HEAD) trains on the base `ime.engine.base_model()` names in M3's deployed code. A new base (`V02_BASE`) needs, before the next Sunday: `models/<base>-hf` on M4 and `~/llm-ime/data/replay/<base>.npz` on home4070 (public samples in its format); without them the week is skipped with the reason in M3's `log/retrain.md`. The old personal model is not used with a new base (`personal_or`). Changing `ime/` or `scripts/` it runs: install again.
- The input method (`shell/`) builds on M4 with the CLT's `swiftc` (`shell/build.sh`, no Xcode); `scripts/deploy_m3.sh` installs it and the engine service on M3 from HEAD (commit first). Top-level Swift code only compiles in a file named `main.swift`.
- The engine service on M3 runs `git archive` code from `~/Library/Application Support/llm-ime/engine`, not the repo there; the repo only lends `.venv` and `models`. Anything else the engine reads at run time must be committed (`ime/char_freq.tsv`); `data/` is not there.
- The shell writes a typing log only on M3 (`~/Library/Application Support/llm-ime/log/`, a `.jsonl` and its summary `.md` per day, 5A.2); read it over ssh, never copy it off M3 (D-019). `shell/build.sh keys` points it at a temporary folder with `LLMIME_LOG_DIR`. The engine service keeps the user's word list (5A.3) beside it in `words.json`; tests and evals use their own (`--words`, `UserWords(path="")`), never M3's.
- The typing log's key-path fields (6A.4: `shell`, `busy`, `flips`, `ctx_ms`) are times and counts taken on the main thread with `systemUptime`, never text, and nothing there may cost more than the clock reads; the full answer after a quick guess was committed (`late_full`) only comes while no newer key has made the engine drop it, so it undercounts fast typing. `scripts/shell_time.py` reads them on M3, by app.
- Answer times in the typing log are from the key, so they include waiting for the forward of the previous key's full search (63% of keys from 4 on, 5B.11) and M3's load: an engine change's cost is measured in one process, alternating key by key while the user is not typing (`scripts/typo_bench.py`), and log windows split with `scripts/answer_wait.py`. Evaluating the two models of a beam step apart (to check `stop` between them) is slower on M3, not faster.
- The candidate window (`shell/Sources/CandidatePanel.swift`) can stay up after a commit (6A.3: seen once on M3, in the Agent Deck input box; 10 of 380 spaces came within 10 ms of the full answer, none of the paths read or tried here left it up): `show` gets a `wanted` closure that the window asks every 0.4 s, and a key with nothing composed hides it. A new way to show it needs the same: only while keys are being typed.
- `LLMEngine.overlap` (5B.13): the prefill and each beam step's forward are only started (`mx.async_eval`) while the keys are read and the next step's edges built; the candidates are the same as with `overlap=0` (run_eval 200 × 3 forms: 0 of 600 differ). Anything that reads `_ctx_logits` or a step's logits must do so after the next `mx.eval` / numpy copy, never from timing code around `_prefill` (`stats["forward_ms"]` is only the launch now).
- The remote engine (7E.1, `ime/remote.py`) runs MLX's CUDA backend on home4070 (`scripts/install_remote4070.sh`, systemd user service `llm-ime-remote`, `~/llm-ime/remote`): MLX compiles kernels at run time and needs the pip CUDA headers as `CUDA_HOME` (`~/llm-ime/cuda-home`) and `MLX_CUDA_SDPA_CACHE_SIZE=8192` (the default 256 dies with "Cache thrashing" after ~150 eval items). A new shape compiles once (seconds cold, cached on disk). Both sides must run the same weights (`model_name`: through the `personal-4bit` link), else M3 computes everything itself. Evals there use public items only (`--src public`); nothing typed is stored on home4070.
- One pass (7D.2, D-050): `Session(two_pass=False)` is the default and the service reads `passes.json` beside the socket (op `passes`, menu item in the shell); the scripts that time or check the full answer (`check_session`, `delay_bench`, `bench_session`, `quick_split`, `repl`) pass `two_pass=True`. `scripts/bench_keys.py` through a service in one pass sees no "full" stage.
